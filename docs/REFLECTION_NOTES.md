# Reflection notes: decisions supported by evidence

This document is a working guide for the author's own account. It does not supply personal experiences, independent-contribution claims, or an application essay. A persuasive reflection connects a real decision to a specific observation and a subsequent change.

## Evidence-linked prompts

| Research moment | Evidence to revisit | Question for the author |
|---|---|---|
| Passing labels did not imply safe execution. | [Paired replay](REPLAY_FINDINGS.md): safe completion remained 4/8. | Which assumption did you hold, and how did this result change it? |
| A stronger gate still had a narrower validity domain. | [Hardlink study](IDENTITY_FINDINGS.md): the resolved gate missed two aliases. | How would you explain path versus object identity in your own words? |
| Time invalidated a correct earlier observation. | [Replacement study](RACE_FINDINGS.md): identity-path gate allowed four protected operations. | What new assumption did this experiment challenge? |
| The improved mechanism still opened protected objects. | Descriptor arm: two protected opens, zero protected content operations. | Why is that distinction necessary for an honest claim? |
| A held object can still change internally. | [Content study](CONTENT_FINDINGS.md): hashing then rereading returns three unapproved versions. | Why does a passing digest fail to authorize a different read? |
| An approved value need not be the newest value. | Verified buffer: zero unapproved deliveries, three approved but stale values. | Which consistency rule should an application require, and who should authorize a new version? |

## Contribution record

For each meaningful session, record what you personally proposed, implemented, checked, explained, or revised. Identify assistance from people, tools, and AI. Separate making a decision from accepting a suggestion, and running an experiment from interpreting its results. The [research log](RESEARCH_LOG.md) records artifacts; your notes should explain your actual role and understanding.

## A useful entry structure

Write a short account containing the initial assumption, the concrete evidence, your decision, the alternative you considered, what changed, and what remains uncertain. Include a link to the relevant commit or result. If your understanding changed after an explanation or code review, say so directly.

## Preparing a portfolio narrative

Choose one authentic episode with a clear intellectual consequence. Explain the technical issue in accessible language, then show what you did and learned. Avoid converting synthetic fixture results into claims of deployed impact, publication, institutional endorsement, or independent invention. The strongest narrative will be one you can defend by explaining the code and evidence yourself.
